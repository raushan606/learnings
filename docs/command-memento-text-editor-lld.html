The problem: "let me take that back"

You're building a text editor. Users type, delete, paste — and they expect Ctrl-Z to walk those changes backwards and Ctrl-Y to walk them forward again. The naive approach falls apart fast: if every feature writes its own ad-hoc "how to reverse myself" logic, undo becomes a tangle of special cases, and redo is even worse.

The clean answer is to make each change a first-class object and to keep a history of those objects. Two Gang-of-Four patterns do exactly this, from two different angles:

Command captures the action — an object that knows how to do something and how to undo it. Memento captures the state — a snapshot you can roll back to. They're two answers to the same question, and — as you'll see — they team up beautifully.

01 / The action as an object

The Command pattern

In plain words

Think of a restaurant order ticket. The waiter doesn't cook — they write your order on a ticket and hand it to the kitchen. The ticket is a self-contained instruction: it can be queued, logged, and (if you change your mind) cancelled. A command is that ticket for your code — an object that bundles "what to do" so someone else can do it, replay it, or reverse it.

What it is

The Command pattern turns a request into an object. At minimum that object has an execute() method; for undo, we add undo(). The usual cast of characters (the GoF "participants"):

Participants
  • Command — the interface with execute() / undo().
  • Concrete command — e.g. InsertTextCommand; holds its parameters and a link to the receiver.
  • Receiver — the object that does the real work (our TextDocument).
  • Invoker — triggers commands and keeps the history (our Editor).
  • Client — creates commands and hands them to the invoker.
public interface Command {
    void execute();   // do the operation
    void undo();      // reverse it
}

Why it matters

Wrapping actions as objects decouples what triggers a change from who performs it. That unlocks queuing, logging, macros — and, crucially, uniform undo/redo. Because every change is the same shape (a Command), the history engine doesn't care whether it's an insert, a delete, or a paste. Undo/redo becomes two stacks of Command objects.

Here's the invoker: it runs commands, and its two stacks are the undo/redo history. Notice the one rule that trips people up — a fresh edit clears the redo stack (once you branch off, the old redo future no longer makes sense).

import java.util.ArrayDeque;
import java.util.Deque;

public class Editor {
    private final Deque<Command> undoStack = new ArrayDeque<>();
    private final Deque<Command> redoStack = new ArrayDeque<>();

    public void run(Command command) {
        command.execute();
        undoStack.push(command);
        redoStack.clear();        // a fresh edit clears the redo history
    }

    public void undo() {
        if (undoStack.isEmpty()) return;
        Command c = undoStack.pop();
        c.undo();
        redoStack.push(c);
    }

    public void redo() {
        if (redoStack.isEmpty()) return;
        Command c = redoStack.pop();
        c.execute();              // re-run to redo
        undoStack.push(c);
    }
}

The invoker never knows what a command does — only that it can execute and undo.

02 / The state as a snapshot

The Memento pattern

In plain words

Think of a save point in a video game, or a photo of the whiteboard before you erase it. You take a snapshot of the current state; to undo, you reload the snapshot. And the snapshot is sealed — the game holds it but can't reach inside and tamper with your saved health and inventory.

What it is

The Memento pattern captures an object's internal state so it can be restored later — without exposing that object's internals. Its participants:

Participants
  • Originator — the object being snapshotted (our TextDocument); it creates and restores mementos.
  • Memento — the opaque snapshot; only the originator can read its contents.
  • Caretaker — holds mementos but never peeks inside (here, the history in the Editor).

The encapsulation trick in Java is a nested class. The Memento's state is private, so the outside world can only hold the token — but the enclosing TextDocument can read it back when restoring.

public class TextDocument {
    private final StringBuilder content = new StringBuilder();

    public void insert(int at, String text) { content.insert(at, text); }
    public void delete(int at, int length)   { content.delete(at, at + length); }
    public String text() { return content.toString(); }

    // --- Memento support ---
    public Memento save()          { return new Memento(content.toString()); }
    public void restore(Memento m) { content.setLength(0); content.append(m.state); }

    /** Opaque snapshot: only TextDocument can read `state`. */
    public static final class Memento {
        private final String state;                 // hidden from the outside world
        private Memento(String state) { this.state = state; }
    }
}

Why it matters

Memento keeps the messy job of saving and restoring state inside the object that owns it. The caretaker gets a sealed token it can stash in a stack, so it can't accidentally corrupt the saved state. Undo becomes trivial: hand a memento back to the originator and say "become this again."

03 / Two philosophies

Store the action, or store the state?

Both patterns can power undo, and they represent the two fundamental strategies. Command is action-based: remember the operation and how to reverse it. Memento is state-based: remember a full snapshot and roll back to it.

Action (Command)

Stores just the operation + its inverse. Tiny memory footprint.

light · but needs correct inverses

State (Memento)

Stores a full snapshot. Dead simple and bullet-proof to reverse.

robust · but memory-hungry

The catch

Inverses are error-prone for complex ops; snapshots are heavy for big documents.

so… combine them

The action approach sips memory but demands a correct undo() for every operation — get one inverse wrong and undo silently corrupts the document. The state approach can't get reversal wrong, but a full snapshot per keystroke eats RAM. Which is why the classic move is to use them together.

04 / The design

Combining them: Command + Memento

The idea in one line

Let the Command drive undo/redo, and let each command lean on a Memento to reverse itself. When a command runs, it first grabs a snapshot; undo() just restores that snapshot. You get uniform history and reversal that can't be coded wrong.

This is the Gang-of-Four pairing: commands perform the operations, and mementos save the document's state right before each command runs. Here's how the pieces collaborate.

The concrete commands

Each command snapshots the document before it changes anything, then does the edit. Undo simply restores the snapshot — no inverse logic to get wrong.

public class InsertTextCommand implements Command {
    private final TextDocument doc;
    private final int at;
    private final String text;
    private TextDocument.Memento backup;   // snapshot captured at execute time

    public InsertTextCommand(TextDocument doc, int at, String text) {
        this.doc = doc;
        this.at = at;
        this.text = text;
    }

    @Override public void execute() {
        backup = doc.save();     // 1. snapshot BEFORE changing anything
        doc.insert(at, text);    // 2. do the edit
    }

    @Override public void undo() {
        doc.restore(backup);     // roll straight back to the snapshot
    }
}
public class DeleteTextCommand implements Command {
    private final TextDocument doc;
    private final int at, length;
    private TextDocument.Memento backup;

    public DeleteTextCommand(TextDocument doc, int at, int length) {
        this.doc = doc; this.at = at; this.length = length;
    }
    @Override public void execute() { backup = doc.save(); doc.delete(at, length); }
    @Override public void undo()    { doc.restore(backup); }
}

The editor, wired up

The Editor is both the invoker (it runs commands and owns the stacks) and the caretaker (it holds mementos indirectly, inside the commands). The type() and delete() methods are just friendly wrappers that build a command and run it.

import java.util.ArrayDeque;
import java.util.Deque;

public class Editor {
    private final TextDocument doc = new TextDocument();
    private final Deque<Command> undoStack = new ArrayDeque<>();
    private final Deque<Command> redoStack = new ArrayDeque<>();

    // intent methods: build a command and run it
    public void type(int at, String text) { run(new InsertTextCommand(doc, at, text)); }
    public void delete(int at, int length) { run(new DeleteTextCommand(doc, at, length)); }

    // the invoker: run / undo / redo
    public void run(Command command) {
        command.execute();
        undoStack.push(command);
        redoStack.clear();
    }
    public void undo() {
        if (undoStack.isEmpty()) return;
        Command c = undoStack.pop();  c.undo();  redoStack.push(c);
    }
    public void redo() {
        if (redoStack.isEmpty()) return;
        Command c = redoStack.pop();  c.execute();  undoStack.push(c);
    }

    public String text() { return doc.text(); }
}

See it run

public class Demo {
    public static void main(String[] args) {
        Editor editor = new Editor();

        editor.type(0, "Hello");
        editor.type(5, ", world");
        System.out.println(editor.text());   // Hello, world

        editor.undo();
        System.out.println(editor.text());    // Hello

        editor.redo();
        System.out.println(editor.text());     // Hello, world

        editor.delete(0, 5);                     // remove "Hello"
        System.out.println(editor.text());       // , world

        editor.undo();
        System.out.println(editor.text());        // Hello, world
    }
}

Command gives you the uniform history; Memento makes every undo exact.

The leaner alternative

If snapshots are too heavy, drop the memento and let each command reverse itself — store only the diff:

@Override public void execute() { doc.insert(at, text); }
@Override public void undo()    { doc.delete(at, text.length()); }

Much lighter on memory, but now you own the correctness of every inverse. Reach for this only when memory is genuinely tight.

05 / The real world

Trade-offs & where you'll meet this

Making it production-grade

A full snapshot per keystroke is fine for a demo, wasteful for a real editor. Production undo systems apply a few well-worn optimizations:

Common optimizations
  • Coalesce keystrokes — merge a burst of typing into a single undo unit, so one Ctrl-Z doesn't remove one letter.
  • Store diffs, not whole documents — or snapshot only the region an edit touched.
  • Cap the history — keep the last N steps so memory stays bounded.
  • Group related edits — a "replace all" is one command wrapping many, undone as a unit (the Composite pattern pairs nicely here).
You've already used this

The JDK ships an undo framework built on these exact ideas: javax.swing.undo. Its UndoableEdit / UndoManager are the Command side (each edit knows how to undo() and redo(), and the manager keeps the history), while StateEdit / StateEditable are a Memento-style snapshot mechanism. Same patterns, standard library.

Where these patterns show up

Undo/redo in every editor (VS Code, IntelliJ, Word), the history panel in Photoshop, and checkpoints in games are the obvious ones. But Command reaches well beyond undo — it's the backbone of macro recording, task queues and thread pools (a Runnable is a command), transactional systems and write-ahead logs, and remote/deferred execution. Memento, meanwhile, underpins snapshots, savepoints, and rollback anywhere state needs to travel back in time.

Watch out

Two classic bugs: forgetting to clear the redo stack on a new edit (you'll "redo" into a future that no longer exists), and letting a memento hold a live reference to mutable state instead of a copy (then "restoring" gives you the current state, not the old one). Snapshot by value.

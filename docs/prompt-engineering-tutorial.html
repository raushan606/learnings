You don't code a model — you brief it

Prompt engineering is the craft of writing instructions that get a language model to do what you want. There's no compiler and no training run. You write text, send it, and read what comes back. If the result is off, you rewrite the instructions and try again — that fast loop is the whole job.

The mental model that helps most: imagine you've just hired a brilliant new teammate. They're fast, widely read, and eager to help — but they have zero context on your project and they take everything you say literally. Your job is to brief them well. The clearer the brief, the better the work.

Why brief the model instead of "training" it? Because prompting is far faster and cheaper than fine-tuning, it keeps everything human-readable, and it keeps working when the model gets upgraded — no retraining required.

What this covers

1 · System vs user prompts — where your rules go vs where the task goes. 2 · Few-shot — teaching by example. 3 · Structured outputs — getting clean data back instead of prose. 4 · Guardrails — keeping it accurate and safe in the real world.

01 / The building blocks

System vs user prompts

In plain words

Think of a stage play. The system prompt is the director's note to the actor before the show — "You're a calm ER doctor. Keep answers short. Never give legal advice." The user prompt is the line the actor actually has to respond to in the scene. The note shapes every response; the line changes every time.

What it is

Every request you send Claude has two kinds of text. The system prompt sets the persona, the rules, and any background that should stay constant for the whole conversation. The user prompt is the specific task or question. In code, this is a top-level system field, plus a list of messages tagged with roles — user for what you send and assistant for Claude's replies.

Why it matters

Two reasons. First, steering: giving Claude a clear role and rules up front reliably lifts the quality and consistency of what comes back. Second, safety: keeping your rules in the system prompt makes them harder to knock over. A user who types "ignore your instructions" is arguing with the script — they're not rewriting the director's notes.

How to do it well

Put the durable stuff in system: who Claude is, the tone, formatting rules, hard limits ("never do X"), and any reference facts. Put only the changing request in the user message. And be specific — "You are a senior Java reviewer; point out bugs and suggest fixes; be blunt" beats "be helpful."

from anthropic import Anthropic
client = Anthropic()

msg = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    system="You are a senior Java code reviewer. Point out bugs "
           "and suggest fixes. Be blunt and concise.",   # the director's note
    messages=[
        {"role": "user",
         "content": "Review: public int div(int a,int b){return a/b;}"}
    ],
)
print(msg.content[0].text)

The system text stays put across turns; only the user message changes.

Where you'd use it
  • A support bot whose personality and boundaries are fixed once, in the system prompt.
  • A coding assistant told its exact role and your team's standards.
  • Any app where many different user questions should all be answered in the same voice and format.
02 / The building blocks

Few-shot prompting

In plain words

It's the difference between telling a new hire "sort these tickets by type" and showing them three tickets you've already sorted correctly. The examples remove all the guesswork about what "correct" actually looks like.

What it is

Few-shot prompting (Anthropic's docs call it multishot) means putting a few worked examples — an input plus the exact output you want — inside your prompt, before the real input. The names just count the examples:

Zero-shot

Instructions only, no examples. "Label this ticket."

One-shot

Exactly one example shown before the real task.

Few-shot

Several examples (usually 3–5) covering the different cases.

Why it matters

Examples show instead of tell. They lock in the format, the tone, and the tricky edge cases far more reliably than describing them in words ever could. This is one of the highest-leverage moves for making output consistent.

How to do it well

Use 3–5 examples that are diverse (cover the cases you actually expect) and relevant. Wrap each one in tags like <example>…</example> so Claude can clearly see where one ends and the next begins.

examples = """
<example><ticket>My card was charged twice.</ticket><label>billing</label></example>
<example><ticket>The app crashes on Export.</ticket><label>bug</label></example>
<example><ticket>Please add a dark mode.</ticket><label>feature</label></example>
"""

msg = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=16,
    system="Label each ticket as exactly one of: billing, bug, feature.",
    messages=[{"role": "user",
        "content": examples + "<ticket>I can't log in after the update.</ticket><label>"}],
)   # Claude continues the pattern -> "bug"
Where you'd use it
  • Classifying text into a fixed set of categories.
  • Extracting fields in an exact shape you demonstrate.
  • Matching a specific writing style or answer format.
03 / Getting usable output

Structured outputs

In plain words

Asking Claude a normal question is like asking someone to write you a letter — you get lovely prose, but your code can't reliably pull facts out of it. Structured output is handing them a form instead. They fill in the boxes, and you get back tidy, predictable fields every single time.

What it is

Structured outputs constrain the reply to a fixed shape — almost always JSON that matches a schema you define — so your program can parse it without guesswork or fragile string-hacking.

Why it matters

The moment Claude's answer feeds code — a database row, a UI component, the next step in a pipeline — you need the same shape every time. Free-form text breaks parsers; a schema-constrained object doesn't.

How to do it in Claude

There are two ways, and you can use them together:

1 · The structured outputs feature (recommended). You pass a JSON schema and Claude's reply is guaranteed to match it. It has two parts: JSON outputs via output_config.format for the final answer, and strict tool use via strict: true to guarantee a tool's inputs match its schema. This is generally available on Claude 4.5 and later models.

msg = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    messages=[{"role": "user",
        "content": "Extract contacts from: 'Call Dana Lee at dana@acme.io or 555-0134.'"}],
    output_config={
        "format": {
            "type": "json_schema",
            "schema": {
                "type": "object",
                "properties": {
                    "name":  {"type": "string"},
                    "email": {"type": "string"},
                    "phone": {"type": "string"},
                },
                "required": ["name", "email", "phone"],
                "additionalProperties": False,
            },
        }
    },
)   # msg.content[0].text is now guaranteed-valid JSON

2 · The tool-use trick (classic). Define a "tool" whose input schema is the shape you want, then force Claude to call it with tool_choice. Instead of prose, it returns arguments that match your schema. This works on older models too.

Tip

Don't write JSON Schema by hand. Generate it from Pydantic (Python) or Zod (TypeScript) — you define a normal class/type and get the schema plus typed parsing for free.

Where you'd use it
  • Data-extraction pipelines that write straight to a database.
  • Classification services returning a label + a score.
  • Agents handing typed results to your app logic or UI.
04 / Making it production-ready

Guardrails

In plain words

Guardrails on a mountain road don't drive the car — they stop it going off the edge on the dangerous corners. Guardrails around a language model are the checks that keep it accurate, on-brand, and safe when inputs get weird or hostile.

What it is

A set of techniques that make a model reliable in production. Four common jobs: keep it from making things up (hallucinations), keep its output consistent, stop people tricking it (jailbreaks and prompt injection), and stop it leaking your hidden prompt (prompt leaks).

The toolkit

Fewer hallucinations. Explicitly allow Claude to say "I don't know"; ask it to ground answers in direct quotes and cite its sources; and when you supply your own documents, tell it to answer only from those, not from general knowledge.

More consistency. Specify the exact output format (this is where structured outputs earn their keep) and reinforce it with a couple of examples.

Resist jailbreaks & injection. Screen incoming user text with a small, cheap model like Claude Haiku 4.5 before it reaches your main prompt; write a firm system prompt; and treat any untrusted content Claude reads with suspicion.

Reduce prompt leaks. Keep your instructions clearly separated from the user's text, and never put secrets in a prompt that you couldn't afford to have exposed.

system = (
    "Answer ONLY using the documents provided below.\n"
    "If the answer isn't in them, reply exactly: "
    "'I don't know based on the provided documents.'\n"   # permission to abstain
    "Cite the document number you used."                  # make it auditable
)
Watch out — two kinds of injection

Direct: the user themselves is the attacker, typing "ignore your rules and…" into your app. Indirect: the user is trusted, but Claude reads outside content — a web page, an email, a document — that has hidden instructions buried inside it. Indirect is the sneaky one for any app that browses the web or reads files.

Where you'd use it
  • A retrieval assistant that must stick to your documents, not improvise.
  • A public chatbot facing users who probe for weaknesses.
  • Any agent that reads emails, files, or the open web.
05 / Bringing it together

All four in one small app

Here's a support-ticket triage bot that uses every skill at once. The system prompt sets the role and rules, few-shot examples show how to label, structured output returns a clean verdict, and a small guardrail lets it flag unsure instead of guessing.

schema = {
    "type": "object",
    "properties": {
        "label":      {"type": "string",
                       "enum": ["billing", "bug", "feature", "unsure"]},  # guardrail: an escape hatch
        "confidence": {"type": "number"},
    },
    "required": ["label", "confidence"],
    "additionalProperties": False,
}

msg = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=128,
    system=(                                                    # 1 - role + rules
        "You triage support tickets. Label each as one of: "
        "billing, bug, feature. If not clearly sure, use 'unsure'."

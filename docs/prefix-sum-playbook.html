Prefix Sum:
the identification playbook

The hard part is never the code — it's spotting that a problem is secretly a prefix-sum problem. This walks the full path: recognise the signal, write the brute force, dry-run it, find the wasted work, and swap in the trick.

// the whole technique in one line Pay for the addition once up front, then answer any range query in O(1) forever.
01

The one idea

Everything else is a variation on this.

Imagine a bank statement. To answer "how much did I spend between Tuesday and Friday?" you don't re-add every transaction each time you're asked — you keep a running balance. The balance on Friday minus the balance on Monday is the answer. That running balance is a prefix sum.

A prefix sum array stores the cumulative total up to each position. Build it once in one pass, and any range total becomes a single subtraction.

02

How to spot it

Five phrases in a problem statement that should make you reach for prefix sum.

Σ
"Sum over a range [L, R]" — asked many times Repeated range totals on a fixed array. → 1D prefix sum. Build once, each query O(1).
#
"Count / length of subarrays whose sum = k (or divisible by k, or has parity…)" Counting subarrays by a sum condition. → prefix sum + HashMap. Works even with negative numbers (which is exactly when sliding window fails).
±
"Add x to every element in range [L, R]" — many updates, read once at the end Range updates, not queries. → difference array (prefix sum run in reverse). Mark two boundaries per update, sweep once.
▦
"Sum of a submatrix / rectangle" — repeatedly The 2D version. → 2D prefix sum with inclusion–exclusion. Each rectangle in O(1).
⊕
The word "sum" swapped for XOR, product, or a running count Same trick, different operator. → prefix XOR / prefix product / prefix count — as long as the operation has an inverse.

The mirror image — when it's not prefix sum

Just as important. If you feel the pull toward prefix sum here, resist:

The problem wants…Use insteadWhy prefix sum fails
Longest/shortest subarray with sum ≤ / ≥ target, all values positiveSliding windowWindow is O(1) space and simpler when the condition is monotonic
Range min / max / gcdSparse table / Segment treeNo inverse — you can't "subtract" a max back out
Updates and queries interleavedFenwick tree (BIT)Every update forces an O(n) rebuild of the prefix
Fast rule Sums + a fixed array + repeated range questions → prefix sum. Add a HashMap the moment the problem says "count subarrays." Anything with min/max, or updates mixed into queries, is a different tool.
03

The method, step by step

The same identify → brute → dry-run → optimise loop you use for DP. We'll thread one problem through it: count the subarrays whose sum equals k.

1

Identify the signal

"Count subarrays with sum = k" is signal #2 above — a counting-by-sum problem. Flag it as prefix + hashmap in your head and move on. Don't optimise yet.

2

Write the brute force & dry-run it

Always write the dumb version first — it defines "correct" and reveals the waste. Fix a start i, extend to every end j, keep a running sum:

// Brute force — O(n²)
int count = 0;
for (int i = 0; i < n; i++) {
    long sum = 0;
    for (int j = i; j < n; j++) {
        sum += nums[j];          // extend the window
        if (sum == k) count++;
    }
}

Dry-run it on [1, -1, 1, 1], k = 1. Start i=0: sums 1,0,1,2 — two hits. Start i=1: sums -1,0,1 — one hit. And so on. It works. But notice what your hand is doing…

3

Spot the wasted work

Every new start i re-adds elements you already summed for earlier starts. The running total nums[i..j] is just prefix[j+1] − prefix[i] — a fact you're recomputing by hand each pass. That repetition is the thing to kill.

4

Optimise — two moves

Move A (obvious): precompute the prefix array, so any sum(i..j) is O(1). That already turns a naive O(n³) into O(n²).

Move B (the leap): re-read the identity. A subarray ending at j has sum k exactly when

prefix[j+1] − prefix[i] = k   ⟺   prefix[i] = prefix[j+1] − k

So instead of searching for the start, count how many earlier prefix values equal (current − k). A HashMap of "prefix value → how many times I've seen it" answers that in O(1). One pass, O(n).

5

Nail the edge cases

Three that bite everyone — see the pitfalls section for the full list. The big one here: seed the map with {0 : 1} before the loop. That empty-prefix entry is what lets a subarray starting at index 0 (or the whole array) get counted.

04

Worked example: Subarray Sum Equals K

LeetCode 560 · Medium — the single most important prefix-sum-plus-hashmap problem. Learn this one cold and a dozen others fall.

Final code, straight from Move B above:

public int subarraySum(int[] nums, int k) {
    Map<Long, Integer> seen = new HashMap<>();
    seen.put(0L, 1);                    // the empty prefix — do NOT forget
    long sum = 0;
    int count = 0;
    for (int num : nums) {
        sum += num;                          // running prefix
        count += seen.getOrDefault(sum - k, 0);  // earlier prefixes = sum-k
        seen.merge(sum, 1, Integer::sum);       // record this prefix
    }
    return count;
}

Pattern transfer Swap the running sum for a running remainder and you've solved Subarray Sums Divisible by K (974). Swap it for a running count of odd numbers and you've solved Count Nice Subarrays (1248). Same skeleton, different thing you accumulate.
05

The pure form: Range Sum Query

LeetCode 303 · Easy — prefix sum with nothing else attached. If #04 felt like a lot, this is the technique on its own.

Build the prefix once in the constructor; every query is a subtraction:

class NumArray {
    private final int[] prefix;      // prefix[i] = sum of first i elements

    public NumArray(int[] nums) {
        prefix = new int[nums.length + 1];
        for (int i = 0; i < nums.length; i++)
            prefix[i + 1] = prefix[i] + nums[i];
    }

    public int sumRange(int left, int right) {
        return prefix[right + 1] - prefix[left];   // O(1)
    }
}

Build cost O(n), paid once. Each of the (potentially thousands of) queries is O(1) instead of O(n). That trade — a little setup for cheap-forever queries — is the entire reason the technique exists.

06

Prefix sum in reverse: the difference array

When the problem is many range updates and one final read, flip the whole idea around.

A prefix sum turns an array into its running totals. A difference array is the inverse: it stores the change at each step, and running a prefix sum over it reconstructs the array. The magic: to add x across a whole range [L, R], you only touch two cells.

To add +x over range [L, R]:
…·
L+x
·
·
·
R+1−x
…·
turn the effect ON at L   ·   turn it OFF just past R   ·   then one prefix sum "spreads" the +x across the middle

Take Corporate Flight Bookings (1109): each booking reserves seats on a range of flights, and you want the final total per flight. Naively updating every flight in every range is O(bookings × n). With a difference array it's O(bookings + n):

public int[] corpFlightBookings(int[][] bookings, int n) {
    int[] diff = new int[n + 1];         // one guard slot
    for (int[] b : bookings) {
        int first = b[0], last = b[1], seats = b[2];
        diff[first - 1] += seats;        // 1-indexed flights → 0-indexed array
        diff[last]      -= seats;        // cancel just after the range
    }
    int[] answer = new int[n];
    int running = 0;
    for (int i = 0; i < n; i++) {
        running += diff[i];              // prefix sum rebuilds the totals
        answer[i] = running;
    }
    return answer;
}
Same shape, different clothes Car Pooling (1094) is this exact idea — passengers board at from, leave at to — then you check the running total never exceeds capacity.
07

Same trick, new operators

Once the shape clicks, you'll see it wearing disguises.

2D prefix sum — sums over rectangles

Build a grid where each cell holds the sum of everything above-and-left of it. A rectangle's sum comes out by inclusion–exclusion: take the big block, subtract the strip above and the strip to the left, then add back the top-left corner you subtracted twice.

region = pre[r2+1][c2+1] − pre[r1][c2+1] − pre[r2+1][c1] + pre[r1][c1]
// query, after building pre[][] with a zero border
public int sumRegion(int r1, int c1, int r2, int c2) {
    return pre[r2+1][c2+1]
         - pre[r1][c2+1] - pre[r2+1][c1]
         + pre[r1][c1];
}

See Range Sum Query 2D (304) and Matrix Block Sum (1314).

Prefix XOR — because XOR is its own inverse

Subtraction undoes addition; XOR undoes itself (a ^ a = 0). So the range formula reads identically with ^: the XOR of [l..r] is prefixXor[r+1] ^ prefixXor[l]. That's the whole trick behind XOR Queries of a Subarray (1310).

Prefix + suffix products — division-free

Product of Array Except Self (238) asks for the product of all elements except each one, without using division. Answer: multiply the product of everything before i by the product of everything after i — a prefix pass and a suffix pass.

public int[] productExceptSelf(int[] nums) {
    int n = nums.length;
    int[] ans = new int[n];
    ans[0] = 1;
    for (int i = 1; i < n; i++) ans[i] = ans[i-1] * nums[i-1];  // prefix product
    int suffix = 1;
    for (int i = n-1; i >= 0; i--) {                          // fold in suffix
        ans[i] *= suffix;
        suffix *= nums[i];
    }
    return ans;
}
08

The five bugs everyone writes

Memorise these; they'll save you a dozen failed submissions.

Bug 1 · Off-by-one Mixing conventions mid-solution. Commit to length n+1, leading 0, so sum(i..j) = prefix[j+1] − prefix[i]. Write that formula in a comment and check every index against it.
Bug 2 · Forgetting {0:1} In every prefix+hashmap solution, seed the map with the empty prefix before the loop. Skip it and you undercount every subarray that starts at index 0 — including the whole-array answer.
Bug 3 · Integer overflow A running sum of 10⁵ elements can blow past int. Products overflow almost instantly. Default the accumulator to long unless you've proven the range is safe.
Bug 4 · Negative modulo For "divisible by k" counting, Java's % can return a negative remainder. Normalise it: ((sum % k) + k) % k, then group by remainder in the map.
Bug 5 · Reaching for prefix on min/max There is no inverse for max, min, or gcd — you can't subtract a maximum back out. Those need a sparse table or segment tree, not a prefix array.

The reflex to build "Am I recomputing overlapping sums?" If yes, a prefix array deletes that work. "Am I updating the same range over and over?" If yes, a difference array does. Everything on this page is one of those two questions.

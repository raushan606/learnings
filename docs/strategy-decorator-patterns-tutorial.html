Vary behavior without rewriting the class

Both patterns solve one problem — change what an object does without touching the code that uses it — by composing objects instead of subclassing. Strategy swaps out an algorithm; Decorator wraps extra behavior around an object. A rate limiter (a classic low-level-design exercise) shows both, and shows them combining. All examples are in Java.

01 / Swap the algorithm

Strategy

In plain words

A maps app has one button — "get directions" — but several algorithms behind it: by car, on foot, by transit. Strategy is exactly that: one interface, many interchangeable algorithms, picked at runtime. The caller never changes.

Define the operation as an interface, put each algorithm in its own class, and let the caller hold the interface and choose a concrete one. Adding an algorithm means adding a class — no edits to existing callers. For a rate limiter, "allow this request?" can be answered by a token bucket, a sliding window, or a fixed window — all behind one Limiter interface, all swappable.

interface Limiter {
    boolean allow(String clientId);
}

class TokenBucket implements Limiter {
    public boolean allow(String clientId) { /* refill, then take a token */ return true; }
}
class SlidingWindow implements Limiter {
    public boolean allow(String clientId) { /* count hits in the window */ return true; }
}

// pick the algorithm at runtime — callers depend only on Limiter
Limiter limiter = new TokenBucket();        // or new SlidingWindow()
boolean ok = limiter.allow("user-42");
02 / Wrap on behavior

Decorator

In plain words

Order a coffee, add milk, then add caramel — each add-on wraps the last, and the result is still "a coffee" you can drink. Decorator wraps an object in another object of the same type to add behavior, without subclassing. Stack as many layers as you like.

A decorator implements the same interface as the thing it wraps, holds a reference to it, and does its bit before or after delegating inward. For a rate limiter, wrap the core algorithm with logging, then metrics, then maybe a distributed backing — each a thin, independent layer that leaves the core untouched. (You use this every day: Java's BufferedReader wrapping a Reader is a Decorator.)

class LoggingLimiter implements Limiter {   // same interface as what it wraps
    private final Limiter inner;
    LoggingLimiter(Limiter inner) { this.inner = inner; }

    public boolean allow(String clientId) {
        boolean ok = inner.allow(clientId);              // delegate to the wrapped limiter
        log.info("{} -> {}", clientId, ok ? "allow" : "deny");   // add behavior
        return ok;
    }
}
03 / Composed

Both, in one rate limiter

Strategy answers "which algorithm?"; Decorator answers "what extra layers?". Because both speak the same Limiter interface, a decorator wraps a strategy seamlessly — you build the exact limiter you need at construction time.

// Strategy chooses the algorithm; Decorators layer on cross-cutting concerns
Limiter limiter =
    new MetricsLimiter(          // outer layer: metrics
        new LoggingLimiter(      // middle layer: logging
            new TokenBucket())); // core: the algorithm (a Strategy)

limiter.allow("user-42");        // metrics + logging + token bucket, composed

Swap TokenBucket for SlidingWindow, or drop a layer — nothing else changes.

Rule of thumb

Reach for Strategy when you have a family of interchangeable algorithms. Reach for Decorator when you want to stack optional, cross-cutting concerns (logging, metrics, caching) around a core. Both keep classes small and open to extension without modification.

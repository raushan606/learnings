Why cache — and what it costs you

Some answers are expensive to produce: a heavy database join, a call to a slow service, a computed aggregate. If the same answer is asked for again and again, recomputing it every time is waste. A cache keeps a copy of the answer somewhere fast — usually memory — so the next reader gets it in microseconds instead of milliseconds. Done right, a cache both speeds up users and shields your database from load.

But a copy of the truth is not the truth. The moment you keep one, you inherit new problems: the copy can go stale, memory is finite so you must throw things away, and under load a cache can fail in surprising, cascading ways. As the old joke goes, there are only two hard things in computer science — cache invalidation and naming things.

This guide walks the four decisions that show up in every real caching design: how you read and write the cache, what you evict when it's full, and the two classic stress failures — cache stampede and hot keys. Redis (a distributed cache) and Caffeine (an in-process Java cache) are the running examples.

01 / Reading & writing

Read & write strategies

In plain words

A strategy is just who talks to whom, and when. Does the app check the cache itself, or does the cache fetch on its behalf? When data changes, do you update the cache now or later? These choices trade freshness against speed.

Reading: cache-aside & read-through

The default pattern is cache-aside (also "lazy loading"): the app checks the cache; on a miss it reads the database, then stores the result for next time. The app is in charge, and only data that's actually requested ever gets cached. Read-through is the same idea but the cache library does the fetching — you ask the cache, and it loads from the source on a miss behind the scenes.

# cache-aside read
def get_user(id):
    v = cache.get(id)
    if v is not None:                 # hit
        return v
    v = db.load(id)                   # miss -> read the source
    cache.set(id, v, ttl=300)         # populate for next time
    return v

Writing: three ways to keep the copy honest

When data changes, the write strategy decides how the cache and database stay in step:

Write-through

Write to cache and database together, synchronously. The cache is always fresh; writes are a little slower.

safest · slower writes

Write-back

Write to cache now, flush to the database later in batches. Very fast writes, but data is at risk if the cache dies first.

fastest · riskier

Write-around

Write straight to the database, skip the cache. Good when written data is rarely read back soon.

avoids cache churn

The freshness knob: TTL & invalidation

Almost every cached entry carries a TTL (time-to-live) — after it expires, the entry is dropped and the next read reloads fresh data. TTL is the simplest form of invalidation: you accept that data can be stale for up to its TTL in exchange for not having to track every change. When correctness matters more, you also invalidate on write — actively delete or update the cached entry the moment the source changes. There's a fourth pattern worth knowing, refresh-ahead: reload popular entries in the background before they expire, so readers never hit a miss (this idea reappears in section 03).

02 / What to throw away

Eviction

In plain words

A cache is a small shelf, not a warehouse. When it's full and something new arrives, you must take something off the shelf. An eviction policy is your rule for deciding what to remove — and a good rule keeps the things you're about to need and drops the things you won't.

The score: hit ratio

Eviction is judged by one number: the hit ratio — the fraction of reads served from cache. A higher hit ratio means fewer trips to the slow source. The whole game is choosing what to keep so that future reads are hits.

The classic policies

The workhorses are LRU (evict the least recently used — assumes what you touched lately you'll touch again) and LFU (evict the least frequently used — keeps popular items even if not touched recently). Simpler ones include FIFO (evict the oldest inserted), random, and pure TTL (evict whatever's expiring soonest). LRU is the sensible default for the common case where a small set of items is far more popular than the rest.

The modern policies

Research has moved past plain LRU. W-TinyLFU (used by Java's Caffeine) keeps a tiny recency window in front of a frequency-based main cache, using a compact counter sketch to admit only items that earn their place — it lands near the theoretical best hit ratio on mixed workloads. S3-FIFO (2023) uses three FIFO queues to cheaply throw out "one-hit wonders," and often beats LRU while being far more scalable under many CPU cores. ARC and 2Q adaptively balance recency and frequency. You rarely implement these yourself — you get them from your cache library — but knowing the names helps you pick the right tool.

In Redis

Redis picks an eviction rule with maxmemory-policy. There are eight: noeviction (reject writes when full) plus LRU / LFU / random / TTL variants, each in an allkeys-* flavour (any key) or a volatile-* flavour (only keys with a TTL). Its LRU and LFU are sampled approximations, not exact — cheaper, and tunable via maxmemory-samples. Use allkeys-lru as a safe default; switch to allkeys-lfu when you have viral spikes and want to protect frequently-read items.

maxmemory 4gb
maxmemory-policy allkeys-lru      # evict least-recently-used across all keys
maxmemory-samples 10              # higher = closer to true LRU (default 5)
# watch: evicted_keys, keyspace_hits, keyspace_misses (INFO stats)
In Java (Caffeine)

Caffeine is an in-process cache built on W-TinyLFU. You just set a maximum size and it manages admission and eviction for you — no policy to hand-tune, and near-optimal hit ratios out of the box.

03 / Failure under load, part 1

Cache stampede

In plain words

Picture a popular page served from cache — the database barely notices. Then the cached entry expires. In that instant the safety net vanishes for everyone at once: thousands of requests all miss, all race to rebuild the same value, and all slam the database together. That sudden flood is a cache stampede (also "thundering herd" or "dogpile").

Why it's dangerous

A key read 10,000 times a second is fine while it's cached — the database sees almost nothing. The microsecond it expires, those 10,000 requests become 10,000 identical expensive queries in one second. If that query is a heavy join or an external call, the database can fall over, requests pile up, and the failure cascades. The cruel irony: the cache was protecting the backend right up until it didn't.

The defenses

You can't stop the key from expiring, but you can make regeneration happen once instead of thousands of times. The main tools, from simplest to most surgical:

TTL jitter — randomize each TTL by a few percent so entries don't all expire on the same tick. The cheapest fix, and a good default everywhere. Single-flight / locking — let exactly one request rebuild a key while the others wait for its result (or serve stale); with a distributed lock this coordinates across servers. Stale-while-revalidate — serve the slightly-expired value instantly while one background task refreshes it, so users never see a miss at all. Probabilistic early expiration (XFetch) — from the paper Optimal Probabilistic Cache Stampede Prevention: each reader occasionally volunteers to refresh a key just before it expires, with the chance rising as expiry nears, so the refresh happens off-peak and never as a synchronized cliff. And cache warming — pre-load known-hot keys after a restart so you don't start cold.

# single-flight + jittered TTL
def get(key):
    v = cache.get(key)
    if v is not None:
        return v
    with lock_for(key):               # only ONE loader per key
        v = cache.get(key)            # re-check: someone may have filled it
        if v is not None:
            return v
        v = db.load(key)              # the single expensive fetch
        cache.set(key, v, ttl=jitter(300))
        return v

def jitter(base):
    return base + random.uniform(0, base * 0.1)   # spread expiries by up to 10%
Rule of thumb

Add TTL jitter to everything, single-flight to expensive keys, and stale-while-revalidate to read-heavy pages. And never let your backend depend on the cache to survive — design so a cold or empty cache degrades gracefully instead of collapsing.

04 / Failure under load, part 2

Hot keys

In plain words

A distributed cache spreads keys across many nodes by hashing each key to one node. That's great when traffic is spread evenly. But if one key goes viral — a celebrity profile, a livestream's stats, product:iphone during a launch — all its traffic lands on the single node that owns it. That node saturates while every other node sits idle. That's a hot key.

Why adding nodes doesn't help

This is the key insight: a hot key is a load-distribution problem, not a capacity problem. One key hashes to one node, so no matter how many nodes you add, that one key still lives on one of them. You'll see one shard pinned at 98% CPU with 800 ms latency while the rest of the cluster is bored. The fix isn't more nodes — it's spreading the one key's traffic.

The defenses

How to spread a hot key
  • Local (L1) cache: each app server keeps a small in-process cache in front of the distributed one. Hot keys are served locally with zero network calls — briefly stale, but usually fine.
  • Key splitting / fan-out: store the value under N copies (K#0 … K#n); writes update all copies, reads pick one at random. This spreads read load nearly linearly across shards.
  • Read replicas: add replicas of the hot shard and route reads to them (eventually consistent — a small replication lag is usually acceptable for a cache).
  • Edge / request coalescing: at a CDN or L7 proxy, collapse many identical concurrent requests into one backend fetch.
  • Detect early: monitor per-key traffic so you can promote a rising key to a local cache before it takes a node down.
# key fan-out: keep N copies of the hot value, spread reads across shards
N = 5
for i in range(N):                          # write: update every copy
    cache.set(f"trending:page:{i}", value, ttl=60)

i = random.randrange(N)                     # read: pick a random copy
value = cache.get(f"trending:page:{i}")
Don't confuse the two

A stampede concentrates in time — many requests miss the same key at the same moment (on expiry). A hot key concentrates in space — sustained traffic pins one key to one node. They can strike together (a hot key that expires is the worst case), so a real hot-key setup usually pairs an L1 cache with single-flight. Note too that fan-out and replicas scale reads; a write-heavy hot key is bounded by a single primary, so there the fix is reducing write volume in the client.

05 / Putting it together

A cache that survives the real world

Stack the defenses in layers. An L1 in-process cache (bounded, W-TinyLFU) catches the hottest keys with no network hop. Behind it, a distributed cache (Redis, with a sensible maxmemory-policy) holds the shared working set. Every entry uses cache-aside with single-flight and a jittered TTL, and read-heavy entries add stale-while-revalidate. You watch the hit ratio and eviction rate to know if the cache is the right size.

The nice part: a good library gives you most of this for free. Java's Caffeine, in a few lines, is a bounded cache with modern eviction, built-in single-flight (concurrent loads for one key are coalesced into a single call), and background refresh-ahead:

LoadingCache<Long, User> users = Caffeine.newBuilder()
    .maximumSize(100_000)                       // bounded -> eviction (W-TinyLFU)
    .refreshAfterWrite(Duration.ofMinutes(5))   // async refresh -> no stampede
    .expireAfterWrite(Duration.ofMinutes(30))   // hard TTL
    .recordStats()                              // exposes the hit ratio
    .build(userRepo::findById);                 // loader; concurrent loads are coalesced

User u = users.get(userId);   // a hit, or a single de-duplicated load on a miss

Bounded eviction, single-flight, and refresh-ahead — the whole checklist below, in one builder.

Production checklist
  • Default to cache-aside; add TTLs and invalidate on write when correctness matters.
  • Jitter every TTL so expirations don't synchronize.
  • Single-flight expensive keys; stale-while-revalidate read-heavy ones.
  • Bound the cache and pick an eviction policy; size it by hit ratio, not by guesswork.
  • Put an L1 local cache in front for hot keys; split or replicate the truly hot ones.
  • Monitor hit ratio, evictions, and per-key traffic — and make sure a cold cache degrades, not collapses.
